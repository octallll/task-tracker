# Отчёт: Task Tracker

## 1. Доменная область

Я сделал простой трекер задач, похожий на канбан-доску. Пользователь создаёт доски (например, «Учёба» или «Работа»),
добавляет на них задачи и переносит их между колонками «К выполнению», «В работе» и «Готово». У задачи можно указать
приоритет и срок, просроченные задачи выделяются красным. Ещё есть теги вроде «срочно» или «backend», они общие для
всех досок.

Для всех сущностей есть полный CRUD, и через REST API, и через веб-интерфейс.

## 2. Стек

| Слой | Технологии |
|---|---|
| Фронтенд | HTML, CSS и JavaScript без фреймворков, раздаётся через nginx 1.27 |
| Бэкенд | Java 21, Spring Boot 3.5 (Web, Data JPA, Validation, Actuator), Lombok |
| СУБД | PostgreSQL 16 |
| Миграции | Liquibase, миграции написаны на SQL |
| Метрики | Micrometer, Actuator (`:8081/actuator/prometheus`), postgres-exporter, VictoriaMetrics |
| Логи | JSON в stdout, Vector (DaemonSet), VictoriaLogs |
| Тесты | JUnit 5, MockMvc, Testcontainers |
| Сборка и запуск | Gradle 8.14, Docker, Docker Compose, Kubernetes (minikube) |

Фронтенд общается с бэкендом по REST (JSON поверх HTTP). Браузер ходит только в nginx, а nginx уже проксирует запросы
`/api/*` на бэкенд, так что адрес бэкенда во фронтенде нигде не прописан.

## 3. Основные сущности

```
┌──────────────┐ 1      N ┌──────────────────┐ N      M ┌─────────────┐
│    Board     │──────────│       Task       │──────────│     Tag     │
├──────────────┤          ├──────────────────┤ task_tags├─────────────┤
│ id           │          │ id               │          │ id          │
│ name         │          │ board_id (FK)    │          │ name UNIQUE │
│ description  │          │ title            │          │ color       │
│ created_at   │          │ description      │          └─────────────┘
└──────────────┘          │ status           │
                          │ priority         │
                          │ due_date         │
                          │ created_at       │
                          │ updated_at       │
                          └──────────────────┘
```

Board (доска) объединяет задачи. Если удалить доску, её задачи удалятся вместе с ней (`ON DELETE CASCADE`).

Task (задача) основная сущность. Статус бывает `TODO`, `IN_PROGRESS` или `DONE`, приоритет `LOW`, `MEDIUM` или
`HIGH`. Срок `due_date` можно не указывать, а `created_at` и `updated_at` заполняются сами. Значения статуса и
приоритета дополнительно проверяются в базе через `CHECK`.

Tag (тег) это метка с уникальным именем и цветом. С задачами теги связаны многие-ко-многим через таблицу
`task_tags`. При удалении тега его связи с задачами тоже удаляются.

### CRUD

| Сущность | Create | Read | Update | Delete |
|---|---|---|---|---|
| Board | `POST /api/boards` | `GET /api/boards`, `GET /api/boards/{id}` | `PUT /api/boards/{id}` | `DELETE /api/boards/{id}` |
| Task | `POST /api/boards/{id}/tasks` | `GET /api/boards/{id}/tasks[?status=]`, `GET /api/tasks/{id}` | `PUT /api/tasks/{id}`, `PATCH /api/tasks/{id}/status` | `DELETE /api/tasks/{id}` |
| Tag | `POST /api/tags` | `GET /api/tags`, `GET /api/tags/{id}` | `PUT /api/tags/{id}` | `DELETE /api/tags/{id}` |

Ошибки API отдаёт в формате `application/problem+json`. Код 400 значит, что пришли неправильные данные, 404 что
сущность не нашлась, 409 что нарушена уникальность (например, тег с таким именем уже есть).

## 4. Соответствие методологии «12 факторов»

### 1. Кодовая база

*Одна кодовая база в системе контроля версий, много развёртываний.*

Весь проект лежит в одном git-репозитории: бэкенд, фронтенд, миграции, Dockerfile-ы и `docker-compose.yml`.
Фронтенд и бэкенд я не стал разносить по разным репозиториям, потому что это одно приложение и выпускаются они
вместе. Любое окружение, будь то dev, staging или prod, разворачивается из этого репозитория, а различаются окружения
только настройками (см. фактор 3).

### 2. Зависимости

*Явно объявляйте и изолируйте зависимости.*

Все библиотеки бэкенда перечислены в `backend/build.gradle.kts`, а их версии задаёт BOM Spring Boot. Сам Gradle тоже
не нужно ставить: Gradle Wrapper скачивает версию 8.14.3, а JDK 21 подтягивается через toolchain. Lombok нужен только
при компиляции (`compileOnly` и `annotationProcessor`), в готовый jar он не попадает.

Окружение изолировано контейнерами. Собирается проект в образе `eclipse-temurin:21-jdk`, а запускается в
`eclipse-temurin:21-jre-alpine`, `nginx:1.27-alpine` и `postgres:16-alpine`, у всех версии зафиксированы. Чтобы
запустить проект, на компьютере нужен только Docker, поэтому ситуации «у меня работает, а у тебя нет» не возникает.
У фронтенда сторонних зависимостей вообще нет.

### 3. Конфигурация

*Храните конфигурацию в окружении.*

Всё, что может отличаться между окружениями, задаётся переменными окружения:
- `DB_URL`, `DB_USER`, `DB_PASSWORD` для подключения к базе;
- `PORT` для порта бэкенда;
- `LOG_LEVEL` для уровня логов;
- `BACKEND_URL` для адреса бэкенда в nginx.

Полный список есть в `README.md`. У параметров базы в `application.yaml` нет значений по умолчанию, поэтому без
переменных приложение просто не запустится и не подключится к какой-нибудь случайной базе. Отдельных профилей под
окружения вроде `application-prod.yaml` тоже нет, файл настроек везде один. Конфиг nginx собирается из шаблона
`default.conf.template` при старте контейнера.

Пароли в репозиторий не попадают: файл `.env` добавлен в `.gitignore`, а в репозитории лежит только пример
`.env.example`.

### 4. Сторонние сервисы

*Рассматривайте сторонние сервисы как подключаемые ресурсы.*

Для приложения PostgreSQL это просто ресурс, который подключается по `DB_URL` с логином и паролем. Работа с базой
идёт через JPA, и коду всё равно, где она запущена. С бэкендом так же: фронтенд находит его по адресу из `BACKEND_URL`.

### 5. Сборка, релиз, запуск

*Строго разделяйте стадии.*

Сборка делается командой `docker compose build`. Она собирает образы `task-tracker-backend:<APP_VERSION>` и
`task-tracker-frontend:<APP_VERSION>`. Dockerfile бэкенда многоэтапный: jar компилируется в одном образе, а в
итоговый образ копируются только JRE и этот jar.

Релиз получается из готового образа и настроек из `.env`. Образ после сборки не меняется, а версия видна по тегу
`APP_VERSION`, поэтому откатиться можно, запустив образ с предыдущим тегом.

Запуск делается через `docker compose up`. Внутри запущенного контейнера ничего не собирается и код не меняется:
если нужно что-то поправить, собирается новый образ.

### 6. Процессы

*Запускайте приложение как процессы без состояния.*

Бэкенд ничего не хранит у себя между запросами: ни сессий, ни кэшей, ни файлов на диске. Все данные лежат в
PostgreSQL, а то, что выбрано в интерфейсе (например, текущая доска), хранится в браузере. Поэтому бэкенд можно
перезапустить когда угодно без потери данных, и он не привязан к конкретной машине.

### 7. Привязка портов

*Экспортируйте сервисы через привязку портов.*

Бэкенд сам по себе HTTP-сервер: API слушает
порт из переменной `PORT`, nginx фронтенда слушает `NGINX_PORT`.

Снаружи доступны два порта: порт фронтенда (`FRONTEND_PORT`) и порт PostgreSQL (`POSTGRES_PORT`). Порт базы оставлен
для разработки, чтобы можно было запускать бэкенд из IDE и подключаться к базе из compose. Бэкенд наружу не открыт,
фронтенд обращается к нему внутри сети compose.

### 8. Параллелизм

*Масштабируйте с помощью модели процессов.*

В приложении два типа процессов: `web` (бэкенд) и `frontend` (nginx), и каждый запускается и перезапускается
отдельно. Сейчас бэкенд работает в одном экземпляре. При этом у него нет состояния (фактор 6) и фоновых задач по
расписанию, так что если понадобится, его можно масштабировать, просто запустив ещё процессы, а не покупая машину
мощнее.

### 9. Утилизируемость

*Максимальная надёжность за счёт быстрого старта и корректного завершения.*

Приложение стартует за несколько секунд. Образ маленький, а JVM настроена на быстрый запуск (`TieredStopAtLevel=1`,
`SerialGC`). Когда бэкенд готов принимать запросы, `/actuator/health` начинает отвечать `UP`, это и проверяет
healthcheck в compose.

При остановке срабатывает graceful shutdown, в Spring Boot он включён по умолчанию. Получив SIGTERM, приложение
перестаёт принимать новые запросы, ждёт до 30 секунд, пока закончатся текущие, и закрывает соединения с базой. Java
запускается через `exec`, поэтому SIGTERM приходит прямо в неё, а не в shell. В compose для этого стоит
`stop_grace_period: 30s`.

Если процесс всё-таки упадёт или его убьют, данные не испортятся, потому что каждая операция выполняется в отдельной
транзакции. После перезапуска всё на месте, так как данные хранятся в PostgreSQL.

### 10. Паритет разработки и продакшена

*Держите окружения максимально похожими.*

Везде используются одни и те же образы и одна и та же база PostgreSQL 16. Тесты
тоже запускаются на настоящем PostgreSQL через Testcontainers. Схема базы везде создаётся одними и теми же
миграциями, а `ddl-auto: validate` при старте проверяет, что сущности в коде совпадают с таблицами. Весь проект
поднимается одной командой `docker compose up --build`, так что развёртывание несложно автоматизировать.

### 11. Логирование

*Рассматривайте логи как потоки событий.*

Приложение пишет логи только в stdout и с файлами логов никак не работает. nginx из официального образа тоже пишет
логи в stdout и stderr. Подробность логов
настраивается через `LOG_LEVEL`.

### 12. Административные задачи

*Выполняйте задачи управления как одноразовые процессы.*

Главная административная задача в проекте это миграции базы. Они написаны на SQL и лежат в репозитории рядом с кодом
(`backend/src/main/resources/db/changelog`), попадают в тот же образ и выполняются с теми же настройками и
зависимостями, что и само приложение. Liquibase применяет их при старте бэкенда, ещё до того, как тот начнёт
принимать запросы. Какие миграции уже выполнены, записывается в таблицу `databasechangelog`, так что повторно они не
запускаются. Руками схему никто не меняет: чтобы что-то изменить, нужно добавить новый файл в `changes/` и подключить
его в `db.changelog-master.yaml`.

Разовые команды тоже выполняются в том же окружении, а не с локальной машины. Например, подключиться к базе можно
так: `docker compose exec postgres psql -U tasktracker tasktracker`.

## 5. Запуск в Kubernetes

Приложение разворачивается в minikube. Все манифесты лежат в папке `k8s/`, файлы пронумерованы в том порядке, в
котором их удобно применять:

| Файл | Что внутри |
|---|---|
| `00-namespace.yml` | Namespace `task-tracker` |
| `01-postgres-secret.yml` | Secret с именем базы, логином и паролем |
| `02-postgres.yml` | Service и StatefulSet для PostgreSQL |
| `03-backend-configmap.yml` | ConfigMap с настройками бэкенда |
| `04-backend.yml` | Service и Deployment бэкенда |
| `05-frontend.yml` | Service (NodePort) и Deployment фронтенда |
| `build-images.sh` | сборка образов и загрузка их в minikube |

### Какие абстракции Kubernetes использованы

**Namespace.** Всё приложение живёт в отдельном пространстве имён `task-tracker`. Так его ресурсы не смешиваются с
остальным, что есть в кластере, и всё можно удалить одной командой `kubectl delete namespace task-tracker`.

**Secret.** Логин и пароль от базы лежат в Secret `postgres`. Postgres берёт из него все переменные целиком
(`envFrom`), а бэкенд только `POSTGRES_USER` и `POSTGRES_PASSWORD`, которые подставляются в его `DB_USER` и
`DB_PASSWORD` через `secretKeyRef`. Так пароль задаётся в одном месте и не дублируется в манифестах.

**ConfigMap.** Остальные настройки бэкенда (`PORT`, `DB_URL`, `LOG_LEVEL`) лежат в ConfigMap `backend` и
подключаются в контейнер как переменные окружения. Это продолжение фактора 3: образ один, а конфигурация приходит
снаружи.

**StatefulSet и PersistentVolumeClaim.** PostgreSQL запущен через StatefulSet, а не через Deployment, потому что у
базы есть состояние. Через `volumeClaimTemplates` для пода создаётся PersistentVolumeClaim на 1 ГБ, minikube сам
выделяет под него том. Данные лежат на этом томе, поэтому переживают перезапуск и пересоздание пода `postgres-0`.

**Deployment.** Бэкенд и фронтенд не хранят состояния, поэтому для них используется Deployment. Он сам создаёт
ReplicaSet, а тот следит, чтобы было запущено нужное число подов. Количество реплик меняется командой
`kubectl scale`, а обновление образа проходит по стратегии RollingUpdate с `maxUnavailable: 0`, то есть новые
поды поднимаются раньше, чем гасятся старые.

**Pod и пробы.** В каждом поде настроены проверки:
- у бэкенда `startupProbe` даёт приложению до 150 секунд на запуск, `readinessProbe` смотрит
  `/actuator/health/readiness` (пока она не прошла, под не получает трафик), а `livenessProbe` смотрит
  `/actuator/health/liveness` и перезапускает зависший контейнер. Отдельно включать эти эндпоинты не пришлось, Spring
  Boot сам включает их, когда видит, что запущен в Kubernetes;
- у фронтенда обе пробы ходят на `/healthz` в nginx;
- у Postgres пробы выполняют `pg_isready`.

Ещё у бэкенда есть init-контейнер `wait-for-postgres`. Он запускается до основного контейнера и ждёт, пока база
начнёт принимать соединения. Без него бэкенд при первом запуске успевал стартовать раньше Postgres, падал и
перезапускался пару раз.

Для всех контейнеров заданы `requests` и `limits` по CPU и памяти, чтобы под не мог занять всю ноду.

**Service.** У каждой части приложения есть свой Service:
- `postgres` и `backend` типа ClusterIP, они доступны только внутри кластера;
- `frontend` типа NodePort (порт 30080), через него приложение открывается снаружи. В minikube удобнее всего
  открыть его командой `minikube service frontend -n task-tracker`.

### Как сервисы взаимодействуют между собой

```
Браузер ──HTTP──▶ Service frontend (NodePort 30080)
                        │
                        ▼
                  Pod'ы frontend (nginx)
                        │  http://backend:8080
                        ▼
                  Service backend (ClusterIP)
                        │  балансирует между репликами
                        ▼
                  Pod'ы backend × N
                        │  jdbc:postgresql://postgres:5432
                        ▼
                  Service postgres (ClusterIP)
                        │
                        ▼
                  Pod postgres-0 ── PVC data-postgres-0
```

Сервисы находят друг друга по именам через DNS кластера. Поды и их IP-адреса постоянно меняются, а у Service адрес и
имя постоянные, поэтому все обращаются не к подам, а к сервисам:

1. Браузер открывает страницу через NodePort-сервис `frontend`, и запрос попадает в один из подов с nginx.
2. nginx отдаёт статику, а запросы на `/api/*` проксирует на `http://backend:8080`. Этот адрес задан переменной
   `BACKEND_URL` в манифесте фронтенда, а имя `backend` резолвится в ClusterIP сервиса бэкенда.
3. Service `backend` раскидывает запросы по всем готовым подам бэкенда. Под попадает в список, только когда прошёл
   readiness-проба, поэтому запросы не уходят в ещё не запустившиеся реплики. Посмотреть, на какие поды сервис
   отправляет трафик, можно командой `kubectl -n task-tracker get endpoints backend`.
4. Бэкенд подключается к базе по `jdbc:postgresql://postgres:5432/tasktracker`, где `postgres` это имя сервиса базы.

Бэкенд можно спокойно масштабировать: состояния у него нет, а миграции при одновременном старте нескольких реплик
выполнит только одна из них, потому что Liquibase перед миграцией берёт блокировку в таблице
`databasechangeloglock`, и остальные реплики её ждут.

### Как запустить

```bash
minikube start --driver=docker --container-runtime=docker

bash k8s/build-images.sh

kubectl apply -f k8s/
kubectl -n task-tracker get pods

kubectl -n task-tracker scale deployment backend --replicas=3
kubectl -n task-tracker get pods

minikube service frontend -n task-tracker
```

Скрипт `build-images.sh` делает то же, что описано в задании: переключает docker на демон внутри minikube
(`eval $(minikube docker-env)`), собирает оба образа и загружает их через `minikube image load`. В манифестах стоит
`imagePullPolicy: IfNotPresent`, поэтому Kubernetes берёт локальные образы и не пытается скачать их из Docker Hub.

## 6. Метрики

### Как это устроено

```
backend pod  ── :8081/actuator/prometheus ──┐
postgres-0   ── :9187/metrics (exporter) ───┤   VictoriaMetrics раз в 15 секунд
                                            │   забирает метрики (pull)
                                            ▼
                     VictoriaMetrics single (namespace monitoring, Helm-чарт)
                     цели находит сама через API Kubernetes по аннотациям prometheus.io/*
```

Метрики собираются по pull-модели. Приложение и экспортер просто отдают текущие значения по HTTP в текстовом формате
Prometheus/OpenMetrics, а VictoriaMetrics сама периодически их забирает и хранит как временные ряды.

Список целей нигде не прописан руками, работает service discovery. В Helm-чарте VictoriaMetrics есть задание сбора
`kubernetes-pods`: VictoriaMetrics спрашивает у Kubernetes список подов и оставляет только те, у которых есть
аннотация `prometheus.io/scrape: "true"`. Порт и путь берутся из аннотаций `prometheus.io/port` и `prometheus.io/path`.
Поэтому если масштабировать бэкенд до трёх реплик, новые поды сразу появляются в сборе, я это проверил: после
`kubectl scale` в метрике `up` стало три пода бэкенда.

### Стек

| Что | Как сделано |
|---|---|
| Хранилище метрик | VictoriaMetrics single, Helm-чарт `vm/victoria-metrics-single`, namespace `monitoring`, values в `k8s/monitoring/vmsingle-values.yaml` |
| Метрики приложения | Spring Boot Actuator + Micrometer + `micrometer-registry-prometheus` |
| Метрики PostgreSQL | `prometheuscommunity/postgres-exporter` как sidecar-контейнер в поде Postgres |
| Обнаружение целей | `kubernetes_sd_configs` с ролью `pod` и аннотации `prometheus.io/*` на подах |

В values-файле включён встроенный в чарт сбор метрик (`server.scrape.enabled: true`), срок хранения 14 дней и диск
на 2 ГБ.

### Экспортеры

**Actuator и Micrometer (встроенный экспортер).** Spring Boot Actuator отдаёт метрики на `/actuator/prometheus`.
Метрики рантайма и фреймворка появляются автоматически, писать ничего не нужно:
- JVM: память (`jvm_memory_used_bytes`), сборка мусора (`jvm_gc_pause_seconds`), потоки, загруженные классы;
- процесс: загрузка CPU (`process_cpu_usage`), время работы, открытые файлы;
- HTTP: число и время обработки запросов по каждому эндпоинту и статусу (`http_server_requests_seconds`);
- пул соединений с базой HikariCP: активные и ожидающие соединения (`hikaricp_connections_active`);
- Tomcat, логи (`logback_events_total`, сколько записей каждого уровня) и время старта приложения.

Actuator вынесен на отдельный порт 8081 (`management.server.port`). Наружу открыт только порт 8080 через nginx,
а nginx проксирует только `/api/`, поэтому метрики и health-check доступны только изнутри кластера, как и требуется.
Пробы Kubernetes тоже ходят на порт 8081. Ко всем метрикам добавляется общая метка
`application="task-tracker-backend"`.

**postgres-exporter (готовый внешний экспортер).** Работает вторым контейнером в поде `postgres-0`. Контейнеры одного
пода делят сеть, поэтому экспортер подключается к базе по `localhost:5432`. Логин и пароль он берёт из того же Secret
`postgres`, что и сама база. Метрики отдаёт на порту 9187, например:
- `pg_up` — доступна ли база;
- `pg_database_size_bytes` — размер базы;
- `pg_stat_database_*` — коммиты, откаты, прочитанные и записанные строки;
- `pg_stat_activity_count` — соединения по состояниям.

### Бизнес-метрики

Бизнес-метрики собраны в классе `TrackerMetrics` (`backend/src/main/java/task/tracker/metrics`) и вызываются из
сервисов при создании досок и задач и при смене статуса задачи.

| Метрика | Тип | Метки | Что считает |
|---|---|---|---|
| `tracker_board_creations_total` | counter | — | сколько досок создано |
| `tracker_task_creations_total` | counter | `priority` | сколько задач создано, по приоритетам |
| `tracker_task_status_changes_total` | counter | `from`, `to` | переходы задач между колонками, например `TODO → IN_PROGRESS` |
| `tracker_tasks_completed_total` | counter | — | сколько задач переведено в `DONE` |
| `tracker_tasks` | gauge | `status` | сколько задач сейчас в каждой колонке |
| `tracker_tasks_overdue` | gauge | — | сколько незавершённых задач уже просрочено |
| `tracker_task_lead_time_seconds` | histogram | — | время от создания задачи до перевода в `DONE` |

Counter только растёт и сбрасывается при перезапуске, поэтому по нему обычно смотрят скорость, например
`rate(tracker_task_creations_total[5m])`. Gauge показывает текущее значение. `tracker_tasks` и
`tracker_tasks_overdue` при каждом сборе метрик считаются запросом к базе, поэтому всегда совпадают с реальными
данными. Если реплик несколько, каждая отдаёт одно и то же число, и складывать их нельзя, правильно брать `max`.
Lead time сделан гистограммой, из неё можно считать среднее и перцентили.

Сначала счётчики назывались `tracker_boards_created_total` и `tracker_tasks_created_total`, но так нельзя: в
OpenMetrics суффикс `_created` зарезервирован (так обозначается время создания счётчика), Micrometer его отрезал, и
счётчик задач вообще пропадал, потому что начинал конфликтовать с gauge `tracker_tasks`. Поэтому в названиях
используется `creations`.

Появление метрик в формате Prometheus проверяет интеграционный тест `businessMetrics`.

### Примеры запросов

| Запрос | Что показывает |
|---|---|
| `up{job="kubernetes-pods"}` | какие цели собираются и доступны ли они |
| `sum by (priority) (increase(tracker_task_creations_total[1h]))` | сколько задач создано за час по приоритетам |
| `max by (status) (tracker_tasks)` | сколько задач сейчас в каждой колонке |
| `tracker_tasks_overdue` | сколько задач просрочено |
| `histogram_quantile(0.9, sum by (le) (rate(tracker_task_lead_time_seconds_bucket[1h])))` | за сколько выполняются 90% задач |
| `sum by (uri, status) (rate(http_server_requests_seconds_count[5m]))` | нагрузка на API по эндпоинтам |
| `pg_up`, `pg_database_size_bytes{datname="tasktracker"}` | состояние и размер базы |

## 7. Логи

### Как это устроено

```
Pod'ы task-tracker (backend, frontend, postgres)
   │ пишут логи в stdout, бэкенд и nginx в JSON
   ▼
Kubernetes сохраняет stdout контейнеров в файлы на ноде: /var/log/pods/...
   │
   ▼
Vector (DaemonSet, namespace logging) читает эти файлы, разбирает JSON,
добавляет метаданные Kubernetes и приводит записи к одной схеме
   │ HTTP, Elasticsearch bulk API
   ▼
VictoriaLogs (StatefulSet + PVC, namespace logging)
   │
   ▼
vmui: kubectl -n logging port-forward svc/victoria-logs 9428:9428 → http://localhost:9428/select/vmui/
```

Все манифесты лежат в `k8s/logging/`:

| Файл | Что внутри |
|---|---|
| `00-namespace.yml` | namespace `logging` |
| `01-victoria-logs.yml` | VictoriaLogs v1.53: StatefulSet, PVC на 2 ГБ, хранение 7 дней, Service на порту 9428 |
| `02-vector-rbac.yml` | ServiceAccount, ClusterRole и ClusterRoleBinding, чтобы Vector мог читать из API имена подов и namespace |
| `03-vector-config.yml` | ConfigMap с конфигом Vector |
| `04-vector.yml` | DaemonSet с Vector 0.59, монтирует с ноды `/var/log` и `/var/lib/docker/containers` только на чтение |

VictoriaLogs я развернул обычными манифестами, а не Helm-чартом, в том же стиле, что и само приложение. Для одного
экземпляра там немного ресурсов: StatefulSet, чтобы данные лежали на постоянном диске, и Service, чтобы до неё могли
достучаться Vector и `kubectl port-forward`.

### Формат логов

Бэкенд пишет логи в JSON во встроенном формате Spring Boot ECS (Elastic Common Schema), это включается одной
настройкой `logging.structured.format.console: ecs`. Пример строки:

```json
{"@timestamp":"2026-10-30T17:51:08.986918962Z","log":{"level":"WARN","logger":"task.tracker.web.ApiExceptionHandler"},
 "process":{"pid":1,"thread":{"name":"http-nio-8080-exec-5"}},
 "service":{"name":"task-tracker-backend","version":"1.0.0","node":{}},
 "message":"GET /api/boards/9999 -> 404: Доска с id=9999 не найден(а)",
 "http":{"request":{"method":"GET"},"response":{"status_code":404}},"url":{"path":"/api/boards/9999"},"ecs":{"version":"8.11"}}
```

Ошибки API (400, 404, 405, 409) бэкенд пишет с уровнем WARN, а непредвиденные исключения с уровнем ERROR и стектрейсом.
Метод, путь и статус добавляются в запись отдельными полями.

nginx пишет access-лог тоже в JSON, с теми же именами полей, что и бэкенд. Уровень считается из HTTP-статуса:
5xx это ERROR, 4xx это WARN, остальное INFO. Ещё есть время ответа `request_time` и адрес, на который nginx проксировал запрос
(`upstream.address`, это ClusterIP сервиса `backend`):

```json
{"@timestamp":"2026-10-30T17:51:08+00:00","log.level":"WARN","service.name":"task-tracker-frontend",
 "message":"GET /api/boards/9999 404","http.request.method":"GET","url.path":"/api/boards/9999","url.query":"",
 "http.response.status_code":404,"http.response.body.bytes":151,"request_time":0.009,
 "upstream.address":"10.99.236.143:8080","upstream.response_time":"0.009","client.ip":"127.0.0.1","user_agent.original":"curl/8.15.0"}
```

Запросы проб Kubernetes к `/healthz` nginx в лог не пишет, чтобы они не забивали его.

Vector при обработке каждой записи:
- разбирает JSON и раскладывает его на поля. VictoriaLogs сама превращает вложенные поля бэкенда в плоские, поэтому
  у бэкенда и nginx поля называются одинаково: `log.level`, `service.name`, `url.path`;
- добавляет метаданные Kubernetes: `kubernetes.pod_name`, `kubernetes.container_name`, `kubernetes.pod_namespace` и
  другие, а лишние (аннотации, UID, ID образов) убирает;
- для строк, которые пришли не в JSON (логи Postgres, старт nginx, postgres-exporter), подставляет
  `service.name = task-tracker-<контейнер>` и определяет уровень: берёт его из поля `level=` или по словам
  `error`/`warn` в тексте. Так у всех записей одна схема, и запросы ниже работают для всех сервисов сразу.

### Почему Vector как DaemonSet

Я выбрал Vector, запущенный как DaemonSet, то есть один под на каждой ноде, который читает файлы логов всех
контейнеров на ней. Почему так:
- **Приложение ничего не знает про систему логов.** Оно просто пишет в stdout, как и требует 12-факторная методология
  (фактор 11). Если завтра поменять VictoriaLogs на что-то другое, код и манифесты приложения не изменятся.
- **Один сборщик на ноду, а не на каждый под.** Сайдкар пришлось бы добавлять в каждый Deployment, и при
  масштабировании бэкенда до трёх реплик было бы три лишних контейнера. DaemonSet один на ноду, а новые поды он
  подхватывает сам.
- **Логи не теряются, если VictoriaLogs недоступна.** Записи остаются в файлах на ноде, а Vector запоминает, до
  какого места дочитал, и дошлёт их позже. При прямой отправке из приложения логи в такой ситуации пропали бы, а само
  приложение тормозило бы на сетевых запросах.
- **В Vector удобно приводить записи к одной схеме.** На языке VRL я в несколько строк разобрал JSON, добавил
  метаданные и уровни для текстовых логов. Fluent Bit тоже так умеет, но конфигурировать сложнее. OpenTelemetry
  Collector для одной задачи доставки логов тяжелее, чем нужно.
- **VictoriaLogs умеет принимать данные в формате Elasticsearch bulk API**, а у Vector для него есть готовый
  sink. Через параметры запроса я указал, какое поле считать текстом (`_msg_field=message`), какое временем
  (`_time_field=@timestamp`) и по каким полям делить логи на потоки (`_stream_fields`: namespace, контейнер, под).

### Запросы LogsQL

Запросы выполнялись во встроенном интерфейсе vmui. Перед этим я создал через приложение доску, задачи и теги,
несколько раз открыл списки, сделал запросы к несуществующим доске и задаче, отправил пустое и некорректное тело,
повторно создал тег с тем же именем и отправил DELETE на `/api/boards`, чтобы в логах были и обычные запросы, и
разные ошибки.

#### (а) Сырые записи за последние 15 минут

```
_time:15m
```

Самый простой запрос: все записи за последние 15 минут без фильтров, новые сверху. На скриншоте видно, что логи
приходят от всех сервисов, а у каждой записи есть разобранные поля: `log.level`, `service.name`, метаданные
Kubernetes. Удобно, чтобы посмотреть, что вообще происходит в системе, и убедиться, что логи доходят.

![(а) сырые записи](docs/logs/01-raw.png)

#### (б) Фильтр по полю: предупреждения бэкенда

```
_time:1h service.name:task-tracker-backend log.level:WARN
```

Оставляет только записи бэкенда с уровнем WARN, то есть все ошибки API, которые вернулись клиенту: 404 на
несуществующую доску и задачу, 400 на пустое имя и сломанный JSON, 405 на неподдерживаемый метод и 409 на
дубликат тега. Из текста и полей `url.path` и `http.response.status_code` сразу видно, какой запрос сломался и
почему. Так ищут причину, когда пользователь говорит, что у него «что-то не работает». Если заменить уровень на
`log.level:ERROR`, будут только серьёзные ошибки.

![(б) фильтр по уровню](docs/logs/02-filter.png)

#### (в) Статистика с группировкой по сервису и уровню

```
_time:1h | stats by (service.name, log.level) count() hits | sort by (hits desc)
```

Считает, сколько записей каждого уровня написал каждый сервис за час. Это общая картина по системе: если у
какого-то сервиса резко выросло число WARN или ERROR, значит, с ним что-то не так. Запрос работает по всем сервисам
сразу именно потому, что Vector привёл их логи к одной схеме полей.

![(в) stats по сервису и уровню](docs/logs/03-stats.png)

#### (г) Самые частые эндпоинты

```
_time:1h service.name:task-tracker-frontend url.path:* | top 5 (url.path)
```

`top` показывает пять путей, к которым чаще всего обращались, по access-логу nginx. Условие `url.path:*` отсекает
текстовые строки старта nginx, у которых этого поля нет. Так видно, какие части API нагружены сильнее всего и на что
в первую очередь смотреть при оптимизации.

![(г) top эндпоинтов](docs/logs/04-top.png)

Ещё один агрегирующий запрос, который я пробовал: время ответа nginx и число разных путей.

```
_time:1h service.name:task-tracker-frontend url.path:* | stats quantile(0.5, request_time) p50, quantile(0.95, request_time) p95, count_uniq(url.path) uniq_paths
```

На моих данных медиана получилась 11 мс, а 95-й перцентиль 83 мс. Самым медленным оказался первый запрос после
перезапуска бэкенда, пока прогревалась JVM.

### Как развернуть

```bash
kubectl apply -f k8s/logging/
kubectl -n logging get pods
kubectl -n logging port-forward svc/victoria-logs 9428:9428
```

После этого vmui открывается по адресу http://localhost:9428/select/vmui/. В новых версиях VictoriaLogs интерфейс
